# v0.7 产品 Brief：系统时区与灵活日期范围

## 1. 背景

当前按天聚合固定使用 UTC+8，完整看板只提供当天、近 7 天、近 30 天和全部。用户需要统计跟随当前 Mac 系统时区，并能查看近 2～6 天、上一整周和任意起止日期。

## 2. v0.7 必做

### 2.1 系统时区切天

- 所有按天统计默认跟随运行 App 的 Mac 系统时区。
- 数据输出必须明确提供当前 IANA 时区 ID，例如 `America/Los_Angeles`。
- “当天”使用系统时区当天 00:00 至当前时刻。
- 修改只影响日期归属，不改变 Token、价格、模型归并、项目归因、去重或 cache 口径。
- 页面不得继续把“今日”标成 UTC+8。

### 2.2 灵活日期范围

完整看板提供：

- 当天
- 近 2 天、近 3 天、近 4 天、近 5 天、近 6 天、近 7 天
- 近 14 天、近 30 天、近 90 天
- 上一整周
- 全部
- 自定义日期

规则：

- “近 N 天”按系统时区自然日计算，包含今天。
- “上一整周”指当前周之前最近的周一至周日。
- 自定义开始日和结束日均包含在统计内；开始日不得晚于结束日。
- 日期范围联动 Hero 总量、折合成本、项目监控、Project Focus、每日图表、图例、项目分布和任务归因。
- 菜单栏 Popover 继续固定展示近 7 天，不增加复杂日期控件。

### 2.3 口径可见性

- 完整看板时间控件旁显示“系统时区 · {IANA ID}”。
- 数据缺少时区元数据时降级显示“系统时区”，不阻断页面。

## 3. v0.7 不做

- 不做运行时切换到北京时间或其他时区。
- 不输出第二套时区数据立方体。
- 不读取或展示对话正文。
- 不改变 5 小时 / 7 天额度窗口含义。
- 不改 Token、计价、去重、cache、模型归并和路径脱敏逻辑。

运行时切换时区需要同一次扫描生成多套按日聚合，或在切换时重新扫描日志；本版本先保证系统时区口径真实可靠。

## 4. 验收标准

1. 在系统时区 `America/Los_Angeles` 下，同一 UTC 时间戳按当地日期归属；跨午夜边界测试通过。
2. `usage.json._meta.timeZone.mode` 为 `system`，并提供非空 `id`。
3. 时间菜单包含近 2～7 天、14 天、30 天、90 天、上一整周、全部和自定义日期。
4. 近 N 天包含系统时区今天；上一整周严格为前一个周一至周日。
5. 自定义日期含首尾，反向输入会被阻止或自动纠正。
6. 切换日期后 Hero、图表、项目和成本视图使用同一范围。
7. 完整窗口和 300px Popover 无横向溢出，console error / warning 为 0。
8. `node --check`、内联脚本编译、`node engine/usage-data.mjs`、`./app/build.sh` 和 `git diff --check` 通过。

## 5. Review 预算

- R1：实现完成后一次 fresh-context 独立 Review。
- 最多允许一次阻断修正和一次定向复核。
